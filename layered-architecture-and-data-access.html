    9. Layered Architecture and Data Access

    The previous examples kept their data in memory. A real application stores it in a database and is organized into layers (see the diagram in the introduction):

    • the web layer (views, forms, templates): read the request, call the business layer, select the template;
    • the business layer: business rules;
    • the DAO layer (Data Access Object): database queries.

    Each layer is aware only of the layer below it, and as few details about it as possible: the web layer is unaware of the queries, and the business layer is unaware of the HTML. This separation makes each layer easier to understand, test, and evolve. Example 28 applies this to managing a list of people: it is, on a smaller scale, the management of doctors and clients from the case study.

    In [Python], database access is organized across several layers:

    • the DB-API 2.0 standard (PEP 249) of [Python] defines a common interface for all SGBD: open a connection, obtain a cursor, execute a SQL command, and read rows. Each SGBD has its own driver: for [MySQL] (and [MariaDB]), [Django] recommends [mysqlclient], a library written in C, installed by the [requirements.txt] example file;
    • ORM (Object-Relational Mapper) from [Django] maps classes (models) to database tables and converts the read rows into objects. It manages connections and transactions, generates the SQL commands itself—tailored to each SGBD—and translates errors from each driver into common exceptions (a uniqueness constraint violation becomes a [IntegrityError], regardless of the SGBD). It follows the so-called Active Record pattern: each object knows how to save itself ([personne.save()]) and delete itself ([personne.delete()]), and each class has a handler ([Personne.objects]) from which requests are sent. This is the model for [Eloquent], the ORM of [Laravel]; [Doctrine], the ORM derived from [Symfony], on the other hand, followed the Data Mapper pattern, where a separate object reads and saves the entities.

    ORM, derived from [Django], is part of [Django] and is one of its key components: the administration interface, the authentication application, database sessions, and generic views all rely on it. It is the equivalent of [JPA] and [Hibernate] in [Java], [Entity Framework Core] to [C#], or [SQLAlchemy] (used with [Flask]) to [Python]. Note a consequence of how [Django] works: by default, each request opens its own connection to the database (upon its first SQL request) and closes it upon termination (upon the [request_finished] signal, example 24). The [CONN_MAX_AGE] setting allows connections to remain open from one request to the next (persistent connections), and [Django] 5.1 added a true connection pool for [PostgreSQL]. Opening a connection to [MySQL] on the same machine takes only a few milliseconds.

    This example requires a running [MySQL] 8.4 or later server (or [MariaDB] 10.11 or later; the minimum versions are [Django] 6.1): The appendix explains how to install one using [Laragon].

    [Django] can also create the tables itself, based on the schemas, using migrations: [Python] files that describe, step by step, the creation and modifications of each table. The [python manage.py makemigrations] command writes these files by comparing the schemas to the state described by the previous migrations; [python manage.py migrate] applies them to the database. This is the standard way of working with [Django]. We maintain a script, SQL, which is common to all versions of the case study and shows exactly what the database contains. Conversely, the command [python manage.py inspectdb] writes the schemas for an existing database: a good starting point, worth reviewing.

    version = models.IntegerField(default=0)
     # the columns VARCHAR(30) and INT

    The file is named [models.py]: this is where [Django] looks for the models of an application declared in [INSTALLED_APPS].

    • Line 8: A template is a class that inherits from [models.Model];
    • Line 10: The primary key, generated by the database ([AutoField]: the [AUTO_INCREMENT] of [MySQL]). [Django] would add it automatically if it were not declared (a field [id], of the type chosen by the setting [DEFAULT_AUTO_FIELD]); we include it here for clarity. It is equal to [None] until the object has been inserted;
    • line 12: the row version. The ORM from [Django] does not have a built-in optimistic lock: it is written by the DAO layer (see below);
    • lines 14–16: the columns. Each class attribute that is a field in the model ([models.XxxField]) corresponds to the column of the same name; the column type is inferred from the field type ([CharField]: [VARCHAR], of length [max_length]; [IntegerField]: [INT]). As in a form (example 08), the fields are declared as attributes of the class, but they are not the same fields: those in [django.db.models] describe columns, while those in [django.forms] describe form fields;
    • lines 19–25: the inner class [Meta] provides information about the template itself. [db_table]: the table name (otherwise, [Django] would take the application name followed by the model name, [personnes_personne]). [managed = False]: The table already exists, and [Django] does not manage it: [makemigrations] will not generate any creation or modification migrations for it. [ordering]: the order of rows when a query does not specify one;
    • lines 28–29: the method [__str__] (Example 12) returns the text representing the object: [str(p)], or [{p}] in an f-string, returns [Marie Pélissier].

    A model is an ordinary class to which methods and properties can be added. The ORM, on the other hand, populates the attributes based on the lines read and generates the commands SQL from the attributes.

    # people/dao.py: the DAO layer, requests, no handling rules

from django.db.models import F

from .models import Personne


# SELECT ... FROM people ORDER BY last name, first name. objects: the GESTIONNAIRE of the model,
# from which all queries originate; all() returns a QuerySet, a query that is
# executed only when its results are read (here, via `list`)
def lister() -> list[Personne]:
    return list(Personne.objects.all())


# SELECT ... FROM people WHERE id = ?; None if the person does not exist
def lire(id: int) -> Personne | None:
    return Personne.objects.filter(id=id).first()


# a person with the same first and last name, other than [sauf_id]. filter: the conditions
# WHERE ; exclude: the conditions WHERE NOT
def homonyme(prenom: str, nom: str, sauf_id: int = 0) -> Personne | None:
    return Personne.objects.filter(prenom=prenom, nom=nom).exclude(id=sauf_id).first()


# INSERT INTO people ...: create constructs the object and saves it
def inserer(prenom: str, nom: str, age: int) -> Personne:
    return Personne.objects.create(prenom=prenom, nom=nom, age=age)


# UPDATE people SET ..., version = version + 1 WHERE id = ? AND version = ?: the
# row is modified only if its version has not changed since it was read (VERROU
# OPTIMISTE). F("version") refers to the column itself, in the order SQL. update
# returns the number of modified rows: 0 if the version has changed
def modifier(id: int, version: int, prenom: str, nom: str, age: int) -> bool:
    lignes = Personne.objects.filter(id=id, version=version).update(
        prenom=prenom, nom=nom, age=age, version=F("version") + 1)
    return lignes == 1


# DELETE FROM people WHERE id = ?
def supprimer(personne: Personne) -> None:
    personne.delete()

    The DAO layer contains only queries, with no business rules. Each function begins with [Personne.objects], the model manager, from which all queries originate.

    • Lines 11–12: [all()] returns a [QuerySet]: an object that describes a query without executing it. The query is sent to the database only when its results are needed (here, when [list] iterates through them): a [QuerySet] is said to be lazy. It can thus be populated before execution ([filter], [exclude], [order_by]...), with each method returning a new [QuerySet]. The order is that of [Meta.ordering];
    • Lines 16–17: [filter(id=id)] adds the condition [WHERE id = ...]; [first()] executes the query, limited to one row ([LIMIT 1]), and returns the first object, or [None]. ([Personne.objects.get(id=id)] would return the object, but would throw the exception [Personne.DoesNotExist] if it did not exist, and the shortcut [get_object_or_404], example 03, would return a 404 error);
    • Lines 22–23: Several conditions in [filter] are combined by [AND]; [exclude] adds a condition [NOT]. The named parameters refer to the fields ([prenom=...]); suffixes specify the comparison: [age__gte=18] ([>=]), [nom__startswith="P"], [nom__iexact=...] (case-insensitive)... The values are transmitted to the database separately and are never copied into the text of the order SQL, which makes injection impossible SQL;
    • lines 27–28: [create] constructs the object and saves it ([INSERT]); after insertion, ORM stores the ID generated by the database in the object. This is equivalent to [p = Personne(prenom=..., ...)] followed by [p.save()];
    • lines 35–38: the update, with its optimistic lock. [update] updates all rows specified by [QuerySet] in a single operation using a single [UPDATE] command, and returns the number of updated rows. The filter has two conditions: the ID and the read version. If another query has modified the row in the meantime—causing its version to change—[UPDATE] does not modify any rows, and the function returns [False]. This is the principle of optimistic locking: nothing is locked, but concurrent modifications are detected. The expression [F("version") + 1] refers to the column itself, in the order SQL ([version = version + 1]): the calculation is performed by the database, not in [Python] based on a value read earlier;
    • Lines 42–43: the deletion: [delete()] sends the [DELETE] from the object’s line.

    Unlike [Doctrine], ORM from [Django] does not have a handler that compares each read object to its original state in order to save only the modified columns: [save()] rewrites all columns of the object (or those of its parameter [update_fields]). This is simpler and more predictable; [update] allows you to write exactly in the desired order.

    # people/metier.py: the MÉTIER layer, the business rules, and only those.
# Every write operation is a TRANSACTION: validated (COMMIT) if the function
# completes normally, or canceled (ROLLBACK) if an exception occurs

from dataclasses import dataclass

from django.db import IntegrityError, transaction

from . import dao
from .models import Personne

HOMONYME = "Une personne porte déjà ces prénom et nom."
MODIFIEE = "Cette fiche a été modifiée entre-temps : rechargez-la."
INCONNUE = "Cette personne n'existe pas (ou plus)."


# a business rule rejects the operation; the message is intended for the user
class MetierErreur(Exception):
    pass


# a person’s data, as transmitted by the web layer
@dataclass(frozen=True)
class DonneesPersonne:
    prenom: str
    nom: str
    age: int


def lister() -> list[Personne]:
    return dao.lister()


def lire(id: int) -> Personne:
    personne = dao.lire(id)
    if personne is None:
        raise MetierErreur(INCONNUE)
    return personne


# with transaction.atomic(): the block is executed within a transaction. The
# database uniqueness constraint (two simultaneous inserts) triggers IntegrityError, which becomes a
# business error
def ajouter(donnees: DonneesPersonne) -> Personne:
    try:
        with transaction.atomic():
             # Rule 1: No two people can have the same first and last names
            if dao.homonyme(donnees.prenom, donnees.nom):
                raise MetierErreur(HOMONYME)
            return dao.inserer(donnees.prenom, donnees.nom, donnees.age)
    except IntegrityError as e:
        raise MetierErreur(HOMONYME) from e


def modifier(id: int, version: int, donnees: DonneesPersonne) -> Personne:
    try:
        with transaction.atomic():
            personne = lire(id)
             # Rule 2: Do not modify a record that has been modified in the meantime by someone else
            if personne.version != version:
                raise MetierErreur(MODIFIEE)
            if dao.homonyme(donnees.prenom, donnees.nom, id):
                raise MetierErreur(HOMONYME)
             # the UPDATE ... WHERE version = ... does not modify anything if another request has
             # modified the row since we read it
            if not dao.modifier(id, version, donnees.prenom, donnees.nom, donnees.age):
                raise MetierErreur(MODIFIEE)
            return lire(id)
    except IntegrityError as e:
        raise MetierErreur(HOMONYME) from e


def supprimer(id: int) -> Personne:
    with transaction.atomic():
        personne = lire(id)
        dao.supprimer(personne)
        return personne
    • lines 12–14: messages from business rules;
    • lines 18–19: an exception class specific to the business layer: a business rule rejects the operation, and the exception message is intended for the user. It inherits from [Exception] without adding anything to it; only its name matters;
    • lines 23–27: a person’s data, as transmitted by the web layer to the business layer: a simple object, unrelated to [Django];
    • lines 34–38: a nonexistent person is a business error;
    • lines 44–52: Rule No. 1: No two people may have the same first and last names. The rule is verified before writing to the database, and a [MetierErreur] exception is thrown if it is not followed. But this verification is not sufficient: two simultaneous requests could both verify that there is no namesake, and then both proceed to insert the record. The database’s uniqueness constraint then rejects the second [INSERT], and the ORM raises a [IntegrityError], which is transformed into the same [MetierErreur]. The database is the last line of defense. [raise ... from e] links the original exception to the new one: the log will show both;
    • lines 55–70: Rule No. 2: Do not modify a record that has been modified in the meantime by someone else. The update form carries the version of the record that was read (in a hidden field); if it differs from the current version, the record has changed since it was displayed. There remains the case where the concurrent modification occurs between reading line 58 and saving line 66: this is detected by the optimistic lock in layer DAO. The function then re-reads the person record to return the new version;
    • lines 73–77: the deletion sets the person to “deleted” for the confirmation message.

    Every operation that writes data is executed within a transaction: [transaction.atomic()], used by [with] (a context manager, example 20), opens a transaction ([BEGIN]) at the beginning of the block; if the block ends normally (even with a [return]), the transaction is committed ([COMMIT]); if an exception occurs within the block, the transaction is rolled back ([ROLLBACK]): none of the changes made within the block are retained, and the exception continues on its path. [transaction.atomic] can also be used as a decorator for an entire function ([@transaction.atomic]). The business layer thus determines the scope of transactions: one business operation equals one transaction. Outside a [atomic] block, ORM operates in “autocommit” mode: each SQL command is committed immediately. A [IntegrityError] is intercepted outside the [with] block: inside the block, the transaction would no longer be usable after the error. Other exceptions (such as a database failure or a programming error) are not business errors: they continue to be processed.

@require_GET
def accueil(request):
    return redirect("personnes_liste")


@require_GET
def liste(request):
    return render(request, "personnes/liste.html", {"personnes": metier.lister()})


# GET: the empty form; POST: the submitted form
@require_http_methods(["GET", "POST"])
def ajout(request):
    titre = "Ajouter une personne"
    action = reverse("personnes_ajout")
    if request.method == "GET":
        return page_formulaire(request, titre, PersonneForm(), action)
    formulaire = PersonneForm(request.POST)
    if not formulaire.is_valid():
        return page_formulaire(request, titre, formulaire, action, statut=422)
    try:
        p = metier.ajouter(formulaire.donnees())
    except MetierErreur as e:
         # a business rule rejects it: the form is redisplayed, with the data entered, and
         # the message at the bottom of the page
        return page_formulaire(request, titre, formulaire, action, erreur=str(e))
    messages.success(request, f"{p} a été ajouté(e).")
    return redirect("personnes_liste")


# GET: the edit form, pre-filled
@require_GET
def modification(request, id):
    try:
        p = metier.lire(id)
    except MetierErreur as e:
        messages.error(request, str(e))
        return redirect("personnes_liste")
    formulaire = PersonneForm(modification=True, initial={
        "prenom": p.prenom, "nom": p.nom, "age": p.age, "version": p.version})
    return page_formulaire(request, "Modifier une personne", formulaire,
                           reverse("personnes_personne", args=[id]), methode="PUT")


# PUT: the update form is submitted; DELETE: the deletion
@require_http_methods(["PUT", "DELETE"])
def personne(request, id):
    if request.method == "DELETE":
        try:
            p = metier.supprimer(id)
            messages.success(request, f"{p} a été supprimé(e).")
        except MetierErreur as e:
             # no form to redisplay: the error is also displayed in a flash message
            messages.error(request, str(e))
        return redirect("personnes_liste")
    titre = "Modifier une personne"
    action = reverse("personnes_personne", args=[id])
    formulaire = PersonneForm(request.POST, modification=True)
    if not formulaire.is_valid():
        return page_formulaire(request, titre, formulaire, action, methode="PUT", statut=422)
    try:
        p = metier.modifier(id, formulaire.cleaned_data["version"], formulaire.donnees())
    except MetierErreur as e:
        return page_formulaire(request, titre, formulaire, action, methode="PUT", erreur=str(e))
    messages.success(request, f"{p} a été modifié(e).")
    return redirect("personnes_liste")
