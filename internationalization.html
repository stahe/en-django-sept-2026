    5. Internationalization

    An internationalized application displays its text in the user’s language. The case study is in French and English. The principle is simple: the templates contain text marked as “to be translated,” and a dictionary for each language associates each text with its translation. The selected language is stored in a cookie.

    [Django] uses [gettext] for this purpose, the translation system from the GNU project, which [Python] also recognizes (the [gettext] module from the standard library), and which is found in many open-source software programs. With [gettext], the key for a text is the text itself, written in the original language: a template written in [{% translate "Accueil" %}], and the English dictionary associates “Accueil” with “Home.” A page thus remains readable and functional even without a dictionary: the text is displayed in the original language. This differs from versions [Symfony], [Laravel], [Flask], [Spring MVC], [ASP.NET Core MVC], and [NestJS] from the case study, which used abstract keys ([MENU.ACCUEIL]). Dictionaries are text files in the [.po] (Portable Object) format, which tools can extract from the code and which translation software can edit; [Django] reads their compiled version, the [.mo] (Machine Object) files. [gettext] can also inflect text into the plural form according to the rules of each language. [Django] is itself translated in this way: it is thanks to its dictionaries that its error messages have been in French since Example 08. The formatting of dates and amounts remains the same as in Example 16.

    # locale/en/LC_MESSAGES/django.po: the English dictionary from Example 22.
# msgid: the original text, as written in the templates (in French);
# msgstr: its translation. This file is compiled into django.mo (the file read by
# Django) using the command: python manage.py compilemessages
msgid ""
msgstr ""
"Language: en\n"
"MIME-Version: 1.0\n"
"Content-Type: text/plain; charset=UTF-8\n"
"Content-Transfer-Encoding: 8bit\n"
"Plural-Forms: nplurals=2; plural=(n != 1);\n"

#: templates/fragments/navbar.html:6
msgid "Accueil"
msgstr "Home"

#: templates/fragments/navbar.html:7
msgid "Produits"
msgstr "Products"

#: templates/pages/accueil.html:4 templates/pages/accueil.html:7
msgid "Bienvenue"
msgstr "Welcome"

#: templates/pages/accueil.html:9
#, python-format
msgid "Bonjour %(nom)s !"
msgstr "Hello %(nom)s!"

#: templates/pages/accueil.html:11
#, python-format
msgid "Nous sommes le %(date)s."
msgstr "Today is %(date)s."

#: templates/pages/produits.html:4 templates/pages/produits.html:7
msgid "Nos produits"
msgstr "Our products"

#: templates/pages/produits.html:9
msgid "Produit"
msgstr "Product"

#: templates/pages/produits.html:9
msgid "Prix"
msgstr "Price"

#: templates/pages/produits.html:21
#, python-format
msgid "%(n)s produit au catalogue."
msgid_plural "%(n)s produits au catalogue."
msgstr[0] "%(n)s product in the catalogue."
msgstr[1] "%(n)s products in the catalogue."

    A [.po] file is a sequence of entries, separated by blank lines:

    • lines 1–4: a comment;
    • lines 5–11: the header entry: an empty string ([msgid ""]), whose “translation” ([msgstr]) contains the dictionary information: the language, the character set, and the language’s plural rule ([Plural-Forms]: in English, two forms, the second for any number other than 1);
    • lines 13–15: a standard entry: [msgid] is the source text, as written in the template; [msgstr] is its translation. The line [#:] indicates where the text was found (a template and a line): this is a comment for the translator;
    • lines 25–28: text containing a variable. In the dictionary, a variable is written as [%(nom)s] (the syntax for format strings from [Python], example 10); the line [#, python-format] flags this to the tools. The translation may reposition the variable or change the punctuation surrounding it (the exclamation point is not preceded by a space in English);
    • lines 47–52: a plural form: [msgid] is the singular form, [msgid_plural] is the plural form, and each form in the translation is numbered ([msgstr[0]], [msgstr[1]]), in the order specified by the rule [Plural-Forms]. In French, 0 and 1 are singular, whereas in English 0 is plural (“0 products”): [gettext] knows this, thanks to this rule. This is an improvement over the “product(s)” used in previous versions of the case study.

    This file is not written by hand. The command:

    1
    python manage.py makemessages -l en

    scans the project’s templates and the [Python] code, extracts all text marked “to be translated,” and creates or updates the [locale/en/LC_MESSAGES/django.po] file: new text is added to it with an empty translation, and existing translations are preserved. All that remains is to write the translations, either in a text editor or in specialized software ([Poedit], for example). The command:

    1
    python manage.py compilemessages

    It then compiles each [.po] file into a [.mo] file—a binary file that is quick to read—which is the one used by [Django]. You must restart the server after a compilation: the dictionaries are loaded once and for all. These two commands use the programs from [gettext] ([xgettext], [msgfmt]...), which must be installed (for [Linux], the [gettext] package; for [Windows], for example, the binaries distributed on the mlocati.github.io website). Since the [django.mo] file is provided with the example, it is not necessary to install these packages to run it.

from pages import views

urlpatterns = [

[^] and [$] mark the start and end of the path; [(?P<code>fr|en)] is a named group: the text it recognizes—[fr] or [en] (the vertical bar means “or”)—is passed to the view in the [code] parameter. Another language does not match any route: [/langue/de] returns a 404 error.

    # pages/views.py: Views are not aware of the language; they provide
# data; the templates translate and format it

from datetime import date

from django.conf import settings
from django.shortcuts import redirect, render
from django.utils.http import url_has_allowed_host_and_scheme
from django.views.decorators.http import require_GET

from .modeles import Produit


@require_GET
def accueil(request):
    return render(request, "pages/accueil.html", {"nom": "Marie", "aujourdhui": date(2026, 9, 23)})


@require_GET
def produits(request):
    return render(request, "pages/produits.html", {"produits": [
        Produit("Clavier", 2500),
        Produit("Souris", 1250),
        Produit("Écran", 114900),
    ]})


# GET /language/en: saves the language selection in a cookie, then returns to the
# previous page
@require_GET
def changer_langue(request, code):
    reponse = redirect(page_d_origine(request))
     # the cookie: valid for one year, unreadable by the JavaScript on the page (httponly),
     # never sent with a request POST originating from another site (SameSite Lax)
    reponse.set_cookie(settings.LANGUAGE_COOKIE_NAME, code, max_age=365 * 24 * 3600,
                       httponly=True, samesite="Lax")
    return reponse


# the page from which the user came (Referer header); if it belongs to the CE site: redirect
# to any address in the request would allow sending
# the user to another site (“open redirect” vulnerability)
def page_d_origine(request):
    referer = request.headers.get("Referer", "")
     # url_has_allowed_host_and_scheme: true for a relative address or an
     # absolute URL where the machine is the one making the request
    if url_has_allowed_host_and_scheme(referer, allowed_hosts={request.get_host()}):
        return referer
    return "/"
    • Lines 14–25: The home and product views do not know the language; they provide raw data (a name, a date, amounts in cents). Translation and formatting are handled by the templates. The class [Produit] has a name and a price in cents; the library [formats] is the one from Example 16: its filter [date_longue] writes a date in the “full” format of the active language (“Wednesday, September 23, 2026,” “Wednesday, September 23, 2026”), and its filter [monnaie] displays an amount;
    • lines 30–37: the language-change view responds by redirecting the user back to the page they came from; the user is returned to their original page in the new language;
    • lines 35–36: The response includes a cookie, which the browser will send back with every request. [set_cookie] receives its name, value, and options: [max_age], its lifetime in seconds (one year); [httponly=True] makes it invisible to the [JavaScript] on the page; [samesite="Lax"] prevents the browser from sending it with a POST request originating from another site. It is added to the response as a [Set-Cookie] header;
    • lines 43–49: the original page is specified by the [Referer] header in the request (the misspelled version, with a single [r], is that of the HTTP standard), which the browser populates with the URL from the page that contained the link. But this header comes from the client, which can put anything in it. Blindly redirecting to this address would turn our application into an open redirect: a malicious link bearing our domain name could send the user to a malicious site. The function [url_has_allowed_host_and_scheme] in [Django] ([django.utils.http]) checks whether an address is relative or whether it points to one of the allowed machines (in this case, the one from the request: [request.get_host()]); otherwise, the user is redirected to the home page.

    [Django] also provides a ready-made view for changing the language, [django.views.i18n.set_language], which performs the same task using a form (POST); we wrote our own to demonstrate it and to allow language switching via a simple link.

    Outside of templates, translation is handled by the functions of the [django.utils.translation] module: [gettext("Accueil")] (often imported under the short name [_]: [_("Accueil")]), [ngettext] for the plural, and [gettext_lazy], a “lazy” translation performed only when the text is used: this is the one to use for text defined when a module is loaded (the label of a form field, for example), when the language of the request is not yet known. The case study uses it.

    The cookie is not signed: it is transmitted in plain text, and the user can modify it. This is not a problem: it contains no confidential information, and [LocaleMiddleware] only accepts the languages specified in the [LANGUAGES] setting. The following example illustrates the level of trust that can be placed in a cookie. Without a cookie, [LocaleMiddleware] reads the browser’s [Accept-Language] header: [curl -H "Accept-Language: en-US,en;q=0.9" http://localhost:8000/] renders the page in English. The two mechanisms thus combine naturally: the browser’s language on the first visit, followed by the language the user has chosen. A third, common approach places the language in the URL ([/en/produits]): the [i18n_patterns] function of [Django] then prefixes the routes with the language, and [LocaleMiddleware] reads it from the path. This case study focuses on the cookie.
