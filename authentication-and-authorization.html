    8. Authentication and Authorization

    Two distinct questions arise for each request:

    • Who is the user? This is authentication: the user has identified themselves with a username and password, and each subsequent request must prove that it comes from them;
    • Do they have permission to access this page? This is authorization: in the case study, only a user with the role ADMIN manages doctors and clients.

    Proof of identity must accompany every request. [Django] has a complete authentication application, [django.contrib.auth]: a [User] model (a database table), middleware that stores the logged-in user in [request.user], login and logout views, permissions, groups, and the administration interface that manages them. It stores the logged-in user in their session (see the chapter on scopes), which is the simplest solution for a web application. The case study, in all its versions ([ASP.NET Core MVC], [Spring MVC], [NestJS], [Flask], [Laravel], [Symfony]), instead uses a JWT token (JSON Web Token), which we will use here: After login, the server generates a token containing the user’s identity and signs it with a secret key (this is the principle behind the signed cookie in Example 23). The token is stored in a cookie; the browser sends it back with every request; the server verifies the signature. The user can read their token but cannot modify it: any modification invalidates the signature. The format is standardized (RFC 7519), understood by all programming languages, and the token includes its expiration date. Most importantly, the server doesn’t have to store anything: any server that knows the key can verify the token.

    The users in the case study are those in their own table, [users], and not those in [django.contrib.auth]; the tokens themselves have no place in [django.contrib.auth]. So we’ll implement the authentication ourselves, using the tools we’re already familiar with, which has the advantage of making everything transparent:

    • a middleware component (Example 03) determines, for each request, who the user is based on the token in their cookie, and includes it in the request ([request.utilisateur], Example 12). The rest of the application sees only this result;
    • decorators (example 08) protect the views: [@connexion_requise], [@role_requis("ADMIN")];
    • passwords are verified using the hashing functions of [Django] ([django.contrib.auth.hashers], which can be used without the rest of the application [auth]);
    • access denials are [PermissionDenied] exceptions, converted into an error page by a [handler403] view (Example 24);
    • Login attempts are limited using the cache in [Django] (Example 27).

    The creation and verification of tokens are handled by the [PyJWT] library, the most commonly used one in [Python], installed by the example file [requirements.txt] (it is imported under the name [jwt]). (There are JWT token libraries for [Django], such as [djangorestframework-simplejwt], designed for API; for a web application, just a few lines are enough, and they better illustrate the mechanism.)

    "admin": ("Administrateur", "ADMIN",
              "pbkdf2_sha256$1500000$UTT2hXVaLIEAuGHPFxgnv9$D9+Owt9lDG14VrvArR3n0GGQXWjY9Sg8cgFwip4+yx4="),
}


def chercher(login: str) -> Utilisateur | None:
    if login not in UTILISATEURS:
        return None
     # "unpacking" a tuple: its three elements into three variables
    nom, role, hachage = UTILISATEURS[login]
    return Utilisateur(login, nom, role, hachage)
    • lines 7–17: a user: the login, the name, the role, the password hash, and the content of the token that authenticated the user (empty for a user read from the user list). The last two attributes have a default value. For a dictionary, this value cannot be written to [claims: dict = {}]: this dictionary would be created only once and shared by all objects. [field(default_factory=dict)] instructs [@dataclass] to call [dict()] for each new object;
    • Lines 20–24: A server never stores a password, even in encrypted form: if the database were stolen, the passwords would be stolen as well (and many people use the same password everywhere). It stores the result of a hash function, a one-way function: you can calculate the hash of a password, but you cannot recover a password from its hash. To verify an entered password, you calculate its hash and compare it to the one stored in the database;
    • lines 25–30: two test users, hard-coded into the program (Example 28 and the case study will populate a database with them): for each login, the name, role, and password hash. The hash was calculated once and for all by the function [make_password] from [Django] (the command is provided in a comment), using its default algorithm, PBKDF2-SHA256. The stored hash has four parts, separated by [$]: the algorithm ([pbkdf2_sha256]), the number of iterations, the salt, and then the result. A good password hashing algorithm has two characteristics. It is intentionally slow, with an adjustable level of slowness: PBKDF2 applies the function SHA-256 1,500,000 times, which takes a few hundred milliseconds—imperceptible to a user, but makes it very costly for a hacker to try billions of passwords; [Django] increases this number with each version to keep pace with computing power (its [auth] application then updates the hashes stored during logins); older hashes remain verifiable, since they include their iteration count. It is salted: a randomly generated salt is mixed with the password before hashing and stored within the hash itself; thus, two users with the same password will have different hashes. [Django] can also use [Argon2] and [bcrypt] (setting [PASSWORD_HASHERS]); the case study, whose database contains hashes [bcrypt], uses the library [bcrypt] directly;
    • lines 33–38: the user of a login, or [None]. [not in] checks for the absence of a key; the assignment [nom, role, hachage = ...] unpacks a tuple: each variable receives the corresponding element.

    # security/auth.py: password verification and tokens JWT

import time

import jwt
from django.conf import settings
from django.contrib.auth.hashers import check_password

from . import utilisateurs
from .utilisateurs import Utilisateur

# the name of the cookie that carries the token
COOKIE = "jeton"


# the user, or None if the login is unknown or the password is incorrect.
# check_password hashes the entered password using the salt and the hashing algorithm
# stored, then compares the two results
def valider(login: str, mot_de_passe: str) -> Utilisateur | None:
    if not login or not mot_de_passe:
        return None
    utilisateur = utilisateurs.chercher(login)
    if utilisateur is None or not check_password(mot_de_passe, utilisateur.hachage_mot_de_passe):
        return None
    return utilisateur


# the user’s token (JWT), signed with the secret key (HMAC-SHA256)
def creer_jeton(utilisateur: Utilisateur) -> str:
    maintenant = int(time.time())
     # the token’s content: the “claims” (statements about the user)
    claims = {
        "sub": utilisateur.login,
        "nom": utilisateur.nom,
        "role": utilisateur.role,
        "iat": maintenant,
        "exp": maintenant + settings.JWT_DUREE_MINUTES * 60,
    }
    return jwt.encode(claims, settings.JWT_SECRET, algorithm="HS256")


# the user described by a token whose signature and expiration date are
# valid; None otherwise (token is forged, expired, or unreadable)
def verifier(jeton: str) -> Utilisateur | None:
    try:
         # Decode verifies the signature ET and the expiration date (claim exp)
        claims = jwt.decode(jeton, settings.JWT_SECRET, algorithms=["HS256"])
    except jwt.InvalidTokenError:
        return None
    return Utilisateur(claims["sub"], claims["nom"], claims["role"], claims=claims)
    • Line 5: the [PyJWT] library;
    • line 7: the function [check_password] from [Django];
    • line 13: the name of the cookie that carries the token;
    • lines 19–25: verification of a username and password. [check_password] reads the algorithm, the number of iterations, and the salt from the stored hash, hashes the entered password using them, and compares the two results (in constant time, e.g., 23). An unknown username and an incorrect password yield the same result, [None];
    • lines 29–39: token generation. Its content is a dictionary of claims about the user. Some have standardized names: [sub] (subject), the user’s identifier; [iat] (issued at), the creation date; [exp] (expiration), the expiration date. Dates are expressed in seconds elapsed since January 1, 1970 ([time.time()] returns this number, including decimals, which [int] omits). The other fields are optional: here, the name and role. [jwt.encode] generates the token and signs it using the algorithm [HS256] (HMAC-SHA256, a signature using a shared secret key);
    • lines 44–50: token verification. [jwt.decode] verifies the signature and expiration date, then returns the assertions. Any anomaly (forged, expired, or malformed token) raises an exception of class [jwt.InvalidTokenError] or one of its subclasses, which the [except] block intercepts. The parameter [algorithms] specifies the list of accepted algorithms: a token that declares a different algorithm (or none at all, [none]) would be rejected. The valid token becomes a [Utilisateur], without a hash, along with its claims (parameter named [claims]).

    # security/middleware.py: AUTHENTIFICATION: for each request, who is the user?

from django.shortcuts import redirect

from . import auth


class Authentification:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
         # By default, the visitor is anonymous
        request.utilisateur = None
        jeton = request.COOKIES.get(auth.COOKIE)
        if jeton is not None:
            utilisateur = auth.verifier(jeton)
            if utilisateur is None:
                 # an invalid token (expired, forged): redirect to /login, and then
                 # the cookie is deleted
                reponse = redirect("login")
                reponse.delete_cookie(auth.COOKIE)
                return reponse
            request.utilisateur = utilisateur
        return self.get_response(request)

    For each request, before the view:

    • line 14: by default, the visitor is anonymous: [request.utilisateur] equals [None];
    • lines 15–17: if the request contains the token cookie, the token is verified;
    • lines 18–23: an invalid token (expired or forged): the middleware responds on its own, without invoking the rest of the process, by redirecting to the login page, and takes the opportunity to delete the cookie: [delete_cookie] adds an empty, already expired cookie to the response;
    • line 24: a valid token: the user it identifies is included in the request. The user is not looked up in the user list: the token is sufficient, since it is signed.

    The middleware does not deny access: it determines who the user is, or determines that the user is anonymous. This is authentication. Denials are handled by access control.

    # security/decorateurs.py: view access control

from functools import wraps

from django.shortcuts import redirect


# @connexion_requise: the view is executed only for an authenticated user; an
# anonymous visitors are redirected to the login page
def connexion_requise(vue):
    @wraps(vue)
    def enveloppe(request, *args, **kwargs):
        if request.utilisateur is None:
            return redirect("login")
        return vue(request, *args, **kwargs)
    return enveloppe

    The decorator [@connexion_requise] wraps a view (Example 08): if the user is anonymous, it responds by redirecting to the login page without calling the view; otherwise, it calls the view. [django.contrib.auth] provides a decorator with the same role, [@login_required], which is based on [request.user].

from django.shortcuts import redirect, render
from django.views.decorators.http import require_GET, require_http_methods, require_POST

from securite import auth
from securite.decorateurs import connexion_requise


@require_GET
def accueil(request):
    return redirect("profil")


# GET: the form; POST: login (the anti-CSRF token was verified by
# CsrfViewMiddleware)
@require_http_methods(["GET", "POST"])
def login(request):
    if request.method == "GET":
        return render(request, "auth/login.html")
    login = request.POST.get("login", "")
    utilisateur = auth.valider(login, request.POST.get("mot_de_passe", ""))
    if utilisateur is None:
         # a deliberately vague message: it doesn’t specify whether it’s the username or the password
        return render(request, "auth/login.html",
                      {"login": login, "erreur": "Login ou mot de passe incorrect."})
     # the token, in a cookie: the page’s JavaScript cannot read it
     # (httponly); it does not accompany requests like POST coming from other sites
     # (samesite); it disappears when the token expires (max_age)
    reponse = redirect("profil")
    reponse.set_cookie(auth.COOKIE, auth.creer_jeton(utilisateur),
                       max_age=settings.JWT_DUREE_MINUTES * 60, httponly=True, samesite="Lax")
    return reponse


# Logout: POST only (a simple link placed on another site cannot
# log the user out without their knowledge); the cookie is deleted
@require_POST
def logout(request):
    reponse = redirect("login")
    reponse.delete_cookie(auth.COOKIE)
    return reponse


# request.utilisateur: the authenticated user, identified by the middleware
@require_GET
@connexion_requise
def profil(request):
    return render(request, "profil/profil.html", {"utilisateur": request.utilisateur})
    • lines 19–22: The login form, hand-coded in the template, is protected against forged requests by the [CsrfViewMiddleware] middleware, just like all POST forms (Example 18);
    • lines 23–28: the login process. If the login fails, the form is redisplayed with the entered username and a deliberately vague message: stating “unknown username” would reveal to a hacker which usernames exist;
    • lines 32–35: if successful, the token is stored in a cookie, and the user is redirected to the protected page (schema PRG). The cookie is [httponly]: the page’s [JavaScript] cannot read it, which protects the token against script injection (XSS); it is [SameSite=Lax]: the browser does not send it with a POST request originating from another site, which protects the application against CSRF attacks; its lifetime ([max_age], in seconds) is the same as that of the token. In production, for HTTPS, we would add [secure=True]: the cookie would never be sent over an unencrypted connection;
    • Lines 40–44: Logging out deletes the cookie ([delete_cookie]). This is a view of POST, protected by the anti-CSRF token: a simple link to [/logout], placed on another site or within an image, cannot log the user out without their knowledge. Note a limitation of tokens: the token itself remains valid until it expires. Someone who has made a copy of it could still use it. That is why their lifetime is limited;
    • Lines 48–51: The protected page. The decorator [@connexion_requise] ensures that [request.utilisateur] is not [None].

from functools import wraps

from django.core.exceptions import PermissionDenied
from django.shortcuts import redirect


# @connexion_requise: the view is executed only for an authenticated user; an
# anonymous visitors are redirected to the login page
def connexion_requise(vue):
    @wraps(vue)
    def enveloppe(request, *args, **kwargs):
        if request.utilisateur is None:
            return redirect("login")
        return vue(request, *args, **kwargs)
    return enveloppe


# @role_requis("ADMIN"): a PARAMÉTRÉ decorator (see Example 08). The view is
# executed only if the authenticated user has the requested role; otherwise, the exception
# PermissionDenied returns a 403 response (see security/erreurs.py)
def role_requis(role):
    def decorateur(vue):
        @wraps(vue)
        @connexion_requise
        def enveloppe(request, *args, **kwargs):
            if not request.utilisateur.a_le_role(role):
                raise PermissionDenied(f"rôle {role} requis")
            return vue(request, *args, **kwargs)
        return enveloppe
    return decorateur
    • lines 23–32: a parameterized decorator (example 08), [@role_requis("ADMIN")]. The wrapper is itself wrapped by [@connexion_requise]: an anonymous visitor is first sent to the login page; an authenticated user who does not have the requested role triggers the [PermissionDenied] exception (example 24), which will result in a 403 (Forbidden) error.

    The difference between the two denial scenarios is significant: an anonymous visitor requesting a protected page is redirected to the login page; an authenticated user who does not have the requested role receives a 403 error—logging in would serve no purpose, since they are already authenticated.

    8.3. Example 27: CAPTCHA and Attempt Limits

def svg(texte: str) -> str:
    l, h = LARGEUR, HAUTEUR
    morceaux = [f'<svg xmlns="http://www.w3.org/2000/svg" width="{l}" height="{h}" viewBox="0 0 {l} {h}">',
                 '<rect width="100%" height="100%" fill="#f5f7fa"/>']
     # the characters: each enlarged, tilted, offset, and each dot slightly
     # randomly shifted
    pas = (l - 20) / len(texte)
    for i, caractere in enumerate(texte):
        echelle = hasard(4.6, 5.6)    # one grid unit in pixels
        angle = hasard(-0.35, 0.35)   # rotation, in radians (approximately ±20°)
        cx = 10 + pas * (i + 0.5) + hasard(-3, 3)    # center of the character
        cy = h / 2 + hasard(-4, 4)
        for trait in POLICE[caractere]:
            d = []
             # range(0, n, 2): 0, 2, 4... one point = two numbers
            for k in range(0, len(trait), 2):
                 # grid point, centered at (2, 3), distorted, rotated, positioned
                x = (trait[k] - 2 + hasard(-0.2, 0.2)) * echelle
                y = (trait[k + 1] - 3 + hasard(-0.2, 0.2)) * echelle
                px = cx + x * math.cos(angle) - y * math.sin(angle)
                py = cy + x * math.sin(angle) + y * math.cos(angle)
                d.append(f"{'M' if k == 0 else 'L'}{px:.1f} {py:.1f}")
            morceaux.append(f'<path d="{" ".join(d)}" fill="none" stroke="{couleur()}" '
                            f'stroke-width="{hasard(2.2, 3):.1f}" stroke-linecap="round" '
                            f'stroke-linejoin="round"/>')
     # 3 scrambling lines: curves that cross the image
    for _ in range(3):
        morceaux.append(f'<path d="M{hasard(0, 20):.1f} {hasard(5, 45):.1f} '
                        f'C{hasard(30, 60):.1f} {hasard(0, 50):.1f} {hasard(90, 120):.1f} '
                        f'{hasard(0, 50):.1f} {hasard(130, 150):.1f} {hasard(5, 45):.1f}" '
                        f'fill="none" stroke="{couleur()}" stroke-width="1.3"/>')
    morceaux.append("</svg>")
    return "".join(morceaux)

        return False

     # correct or not

    # security/limiteur.py: the limit on login attempts per address IP

import time

from django.conf import settings
from django.core.cache import cache


# A client’s failed attempts are counted within a fixed time window: at most
# LOGIN_MAX_ECHECS failures per window of LOGIN_FENETRE_SECONDES seconds
class Limiteur:
    def __init__(self, ip: str):
        self.cle = f"login.{ip}"

     # seconds to wait if the client is blocked, 0 otherwise
    def attente(self) -> int:
        etat = cache.get(self.cle)
        if etat is None or etat["echecs"] < settings.LOGIN_MAX_ECHECS:
            return 0
        return max(1, int(etat["fin"] - time.time()))

     # one more failure
    def echec(self) -> None:
        etat = cache.get(self.cle)
        if etat is None:
             # a new window begins
            etat = {"echecs": 0, "fin": time.time() + settings.LOGIN_FENETRE_SECONDES}
        etat["echecs"] += 1
         # the key is removed from the cache at the end of the window (timeout, in seconds)
        cache.set(self.cle, etat, timeout=max(1, int(etat["fin"] - time.time())))

     # A successful connection clears the failures
    def effacer(self) -> None:
        cache.delete(self.cle)

    The limiter counts a client’s failed attempts within a fixed time window: no more than three failed attempts per 60-second window, counted from the first failed attempt. Each client is identified by its address IP.

    • line 13: the cache key, specific to the client: [login.127.0.0.1];
    • lines 16–20: the number of seconds to wait if the client is blocked (the number of failures has reached the maximum), 0 otherwise. The state stored in the cache is a dictionary: the number of failures and the end time of the window;
    • lines 23–30: one more failure. If there is no state in the cache, a new window begins. The state is rewritten with a lifetime that expires at the end of the window: the cache will then automatically forget it, and the client will start over from scratch;
    • lines 33–34: a successful connection clears the failures.

    This limiter, written for illustrative purposes, has a weakness: two simultaneous failures could read the same state and count it as only one. The cache in [Django] offers atomic operations ([cache.add], which writes only if the key does not exist, and [cache.incr], which increments a number), which are used in the case study version. Ready-made libraries are also available ([django-ratelimit], [django-axes]).

# GET: the form; POST: login, with CAPTCHA and attempt limit
@require_http_methods(["GET", "POST"])
def login(request):
    if request.method == "GET":
        return page_login(request)
    login = request.POST.get("login", "")
     # the client limiter for CE: its failed attempts are counted under its address IP
    limiteur = Limiteur(request.META["REMOTE_ADDR"])
     # 1. A blocked address is not even listened to
    secondes = limiteur.attente()
    if secondes > 0:
        return page_login(request, login, f"Trop de tentatives : réessayez dans {secondes} s.")
     # 2. First the CAPTCHA (low-cost), then the password (PBKDF2, high-cost)
    if not captchas.verifier(request.POST.get("captcha_id", ""), request.POST.get("captcha", "")):
        limiteur.echec()
        return page_login(request, login, "Le code de l'image est incorrect.")
    utilisateur = auth.valider(login, request.POST.get("mot_de_passe", ""))
    if utilisateur is None:
        limiteur.echec()
        return page_login(request, login, "Login ou mot de passe incorrect.")
    limiteur.effacer()
    reponse = redirect("profil")
    reponse.set_cookie(auth.COOKIE, auth.creer_jeton(utilisateur),
                       max_age=settings.JWT_DUREE_MINUTES * 60, httponly=True, samesite="Lax")
    return reponse

def page_login(request, login="", erreur=None):

                  {"login": login, "erreur": erreur, "captcha": captchas.generer()})

# log the user out without their knowledge); the cookie is deleted

    reponse = redirect("login")
    reponse.delete_cookie(auth.COOKIE)
    return reponse
